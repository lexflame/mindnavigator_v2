# Доменные правила задач MindNavigator

Дата фиксации: 2026-06-07

## Назначение

Документ описывает действующие правила задач, которые должны сохраняться при выделении
`TaskTypeService`, `TaskHierarchyService` и `ProjectContextService`. Источником фактического
поведения остаются storage-методы и автоматические тесты; расхождения между этим документом
и кодом должны устраняться явно.

Основные реализации:

- `mindnavigator/services/task_type_service.py`;
- `mindnavigator/storage/database_tasks_mixin.py`;
- `mindnavigator/storage/database_project_properties_mixin.py`;
- `mindnavigator/workspaces/tasks/tasks_model.py`;
- `mindnavigator/workspaces/tasks/task_edit_dialog.py`;
- `mindnavigator/workspaces/tasks/task_details_dialog.py`.

## Базовая модель

Задача может одновременно иметь:

- дату и необязательное время;
- приоритет и важность от 1 до 5;
- колонку доски и признак выполнения;
- проект и родительскую задачу;
- встроенный тип: обычная или плановая задача;
- проектный тип задачи;
- цветовой и тематический маркеры;
- повторение, порядок внутри плана и служебные данные выполнения.

`project_task_type_id` ссылается только на активный тип того же проекта, который указан в
`project_id`. Если проект отсутствует, тип не существует, неактивен или принадлежит другому
проекту, storage нормализует `project_task_type_id` в `None`.

## Встроенные типы

В интерфейсе доступны два встроенных типа:

- обычная задача: `project_task_type_id = None`, `is_plan_task = False`;
- плановая задача: `project_task_type_id = None`, `is_plan_task = True`.

Выбор встроенного типа для корня дерева распространяет на всех потомков текущие значения
корневой задачи:

- `project_id`;
- `priority`;
- `importance`;
- `is_plan_task`;
- `marker_color`;
- `marker_theme`.

У потомков при этом очищается `project_task_type_id`. Каскад можно подавить только внутренним
параметром storage `suppress_builtin_type_cascade`; это технический механизм для пакетных
обновлений модели, а не пользовательское доменное правило.

## Проектные типы задач

Проектный тип принадлежит одному проекту и задает:

- уникальные внутри проекта `title` и `value`;
- уникальный непустой цветовой маркер;
- тему маркера;
- необязательный приоритет;
- важность от 1 до 5;
- признак плановой задачи;
- необязательную концепт-доску;
- активность и порядок отображения.

При создании или обновлении задачи проектный тип переопределяет переданные значения
приоритета, важности, плановости и непустых маркеров своими defaults. Если у типа задана
концепт-доска, задача прикрепляется к ней.

Применение проектного типа к задаче распространяет на все ее дерево:

- проект, которому принадлежит тип;
- идентификатор проектного типа;
- важность и плановость;
- непустые приоритет и маркеры типа;
- связь с концепт-доской, если она задана.

Изменение активного проектного типа повторно применяет его defaults ко всем задачам этого
типа и их потомкам.

## Деактивация и удаление проектного типа

Проектный тип, используемый задачами, удалять нельзя. Вместо удаления он деактивируется.

При деактивации все непосредственно помеченные этим типом задачи получают:

- отложенный приоритет;
- колонку доски `deferred`;
- причину `project_task_type_deactivated`;
- идентификатор типа в `postponed_by_project_task_type_id`.

При повторной активации служебная причина очищается, задачи возвращаются в очередь, а defaults
типа снова применяются к деревьям. Если перед восстановлением приоритет оставался отложенным,
он временно заменяется на `Medium`, после чего непустой приоритет типа имеет преимущество.

Неиспользуемый тип можно удалить физически.

## Иерархия задач

Иерархия задается через `parent_id` и должна оставаться ацикличной.

При переносе задачи:

- задача не может стать родителем самой себе;
- задача не может быть перемещена под собственного потомка;
- отсутствующий родитель отклоняется;
- плановый элемент нельзя переподчинить отдельно от его текущего родителя;
- проект новой подзадачи определяется по проекту верхнего родителя цепочки, а не по ближайшему
  родителю.

При возврате задачи в корень ее текущий проект сохраняется. Перенос к расписанию родителя
меняет дату и время, но сам по себе не меняет иерархию.

## Плановые задачи и элементы плана

Корневая задача с `is_plan_task = True` образует план. Ее вложенные задачи рассматриваются как
элементы плана независимо от собственного флага `is_plan_task`.

Для элементов плана действуют правила:

- проект наследуется от верхнего корня;
- ручная смена проекта элемента не должна нарушать проект корня;
- отдельное переподчинение элемента запрещено;
- порядок хранится в `plan_order` среди задач одного родителя;
- для элемента поддерживается оценка длительности;
- изменение проекта корня синхронизирует проект вложенных элементов плана.

Флаг `is_plan_task` редактируется у корневой задачи. В формах вложенной задачи управление
плановостью отключено, чтобы не создавать конкурирующие источники состояния.

## Проектный контекст

Проект влияет на задачу через несколько независимых правил:

- `default_task_priority` переопределяет приоритет задачи;
- `force_recurrence_kind` принудительно задает допустимое повторение;
- связанные карта, заметка и объект добавляются как attachments;
- проектные отображаемые свойства доступны в карточке задачи;
- проектные типы доступны только для своего проекта;
- вложенная задача использует проект верхнего корня иерархии.

Приоритет проекта применяется после defaults проектного типа. Следовательно, при конфликте
непустой `default_task_priority` проекта является итоговым значением.

## Другие каскады

Переход приоритета корневой задачи в отложенный или обратно распространяет новый приоритет на
всех потомков. Остальные изменения приоритета сами по себе не запускают этот отдельный каскад.

Изменения, затрагивающие дерево, должны выполняться атомарно. После успешной записи UI-модель
обязана перечитать или согласованно обновить все затронутые строки, а не только выбранную.

## Инварианты для будущих сервисов

Будущие доменные сервисы должны обеспечить следующие условия:

1. UI передает намерение пользователя и не собирает каскад из отдельных CRUD-вызовов.
2. Проверка принадлежности проектного типа проекту выполняется до изменения дерева.
3. Все изменения одного дерева выполняются в одной транзакции.
4. Обход иерархии защищен от циклов и отсутствующих родителей.
5. Проект вложенной задачи вычисляется из верхнего корня единым способом.
6. Применение и снятие типа возвращает список затронутых задач для точного обновления UI.
7. Деактивация типа обратима и не уничтожает пользовательские задачи.
8. Новые правила сопровождаются storage-тестами на корень, потомка и глубокого потомка.

## Известные ограничения текущей реализации

- `TaskTypeService` уже является публичной точкой применения типа из `TasksModel`, но SQL-каскады
  пока остаются внутри storage-методов.
- Некоторые операции после записи перечитывают полный список задач.
- Применение проектного типа к дереву обновляет всех потомков, даже если ранее у них были
  собственные типы или настройки.
- Автоматическое прикрепление к концепт-доске добавляет связь, но снятие типа не удаляет ранее
  созданную связь.
- Правила приоритета проекта и типа имеют неочевидный порядок применения и должны быть
  инкапсулированы одним сервисом до дальнейшего расширения.

Эти ограничения являются входными данными для `P1-03`, а не разрешением менять поведение без
миграционного решения и тестов совместимости.
