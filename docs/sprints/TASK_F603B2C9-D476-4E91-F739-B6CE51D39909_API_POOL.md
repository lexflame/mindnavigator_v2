# API Pool Notes: TASK_F603B2C9-D476-4E91-F739-B6CE51D39909

## Title
Publish the entity API pool self-description schema and usage examples for AI clients.

## Self-Description Schema
1. `EntityApiPool.describe()` returns a machine-readable payload with these top-level fields:
- `service_name`
- `api_name`
- `protocol_version`
- `schema_version`
- `compatible_clients`
- `codex_compatible`
- `handshake`
- `operations`
- `entity_kinds`
- `examples`

2. `handshake` semantic fields:
- `connect_operation`: the bootstrap entrypoint name (`describe`)
- `purpose`: the human-readable contract summary
- `required_client_fields`: required client metadata (`client_name`)
- `optional_client_fields`: optional client metadata (`client_version`, `capabilities`)

3. `operations` entries describe endpoint contracts:
- `name`: stable operation identifier
- `summary`: semantic description
- `parameters`: ordered parameter names
- `returns`: result envelope kind
- `idempotent`: request safety hint

4. `entity_kinds` entries describe data and action support per entity type:
- `kind`, `title`, `identity_field`
- `list_fields`: fields guaranteed in list/read payloads
- `mutable_fields`: fields accepted by create/update flows
- `execute_actions`: supported domain actions for `execute_entity_action`

## Endpoint Catalog
1. CRUD endpoints:
- `list_entities(entity_kind, filters=None, limit=None, offset=0)`
- `get_entity(entity_kind, entity_id)`
- `create_entity(entity_kind, payload)`
- `update_entity(entity_kind, entity_id, payload)`
- `delete_entity(entity_kind, entity_id, force=False)`

2. Action endpoint:
- `execute_entity_action(entity_kind, entity_id, action, payload=None)`

3. Supported entity kinds:
- `task`
- `project`
- `note`
- `idea`
- `object`
- `map`
- `collection_item`

4. Supported execute actions:
- `task`: `mark_done`, `mark_pending`, `toggle_done`
- `project`: `archive`, `unarchive`
- `note`: `favorite`, `unfavorite`, `lock`, `unlock`
- `idea`: `promote`, `archive`, `unarchive`
- `object`, `map`, `collection_item`: no execute actions

## AI Client Usage
1. Bootstrap flow:
- call `connect(client_name, client_version, capabilities)`
- verify `codex_compatible == true`
- read `operations` and `entity_kinds`
- cache `protocol_version` and `schema_version`

2. Codex adapter flow:
- `CodexEntityAdapter.handshake()` performs the compatibility check before each request
- adapter methods proxy directly to the service after the handshake succeeds
- handshake failure raises `EntityApiError`

3. Mutation guarantees:
- write endpoints return normalized entity payloads after persistence
- `delete_entity` returns a deterministic delete envelope
- `execute_entity_action` returns `entity_kind`, `entity_id`, `action`, `entity`, and `payload`

## Examples
1. Bootstrap request:
```json
{
  "client_name": "codex",
  "client_version": "2026.03",
  "capabilities": ["crud", "execute"]
}
```

2. Bootstrap response excerpt:
```json
{
  "api_name": "mindnavigator.entity_api",
  "protocol_version": "1.0",
  "schema_version": "2026-03-02",
  "codex_compatible": true
}
```

3. CRUD example:
```json
{
  "operation": "create_entity",
  "entity_kind": "task",
  "payload": {
    "title": "Prepare sprint",
    "day": "2026-03-02"
  }
}
```

4. Execute example:
```json
{
  "operation": "execute_entity_action",
  "entity_kind": "task",
  "entity_id": 42,
  "action": "mark_done",
  "payload": {}
}
```

## Versioning And Compatibility
1. `protocol_version` covers wire-level method semantics.
2. `schema_version` marks the self-description payload revision.
3. AI clients should fail closed when required operations or fields are missing.
4. Backward-compatible additions should prefer new fields and new actions over breaking field renames.
