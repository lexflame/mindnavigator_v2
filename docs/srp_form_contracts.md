# Формы СРП: терминология и фактические контракты

Документ фиксирует термин **«Форма СРП»** для интерфейсов создания,
просмотра и редактирования задач, проектов и типов задач. СРП в этом
контексте означает три режима одной пользовательской поверхности:

- **С**оздание (`create`);
- **Р**едактирование (`update`);
- **П**росмотр (`read`).

Форма СРП является логическим UI-контрактом, а не требованием иметь один
класс на все три режима. Нормативными считаются перечисленные ниже текущие
маршруты. Старые диалоги, которые не входят в эти маршруты, не должны
использоваться как образец для новой функциональности.

## Форма СРП задач

### Классы и режимы

| Режим | Реализация | Контракт |
| --- | --- | --- |
| `create` | `TaskCreateDialog(TaskDetailsDialog)` в `mindnavigator/workspaces/tasks/task_create_dialog.py` | Работает с временным `TaskRow(id=0)`. Inline-изменения остаются локальными до подтверждения формы. |
| `read` | `TaskDetailsDialog` в `mindnavigator/workspaces/tasks/task_details_dialog.py` | Открывается с существующим `TaskRow`; редакторы и действия изменения выключены. |
| `update` | тот же `TaskDetailsDialog` после `start_editing()` или кнопки «Редактировать» | `_set_form_editing(True)` включает редакторы; `_save_form_updates()` сохраняет текущие значения и возвращает форму в read-режим. |

`TaskEditDialog` в `task_edit_dialog.py` является legacy-реализацией. Он ещё
покрыт отдельными тестами совместимости, но не является актуальной Формой СРП
для маршрута редактирования из списка задач.

### Запись

Создание проходит по цепочке:

1. `TasksWorkspace.open_create_task_dialog()` открывает `TaskCreateDialog`.
2. До подтверждения `_save_inline_updates()` меняет только временный `TaskRow`.
3. После `Accepted` workspace вызывает `TasksModel.add_task()`.
4. Модель вызывает storage-метод `create_task()`.
5. Только после получения положительного `task.id` применяются отложенные context links.

Начальная Kanban-стадия передаётся как `board_column` через форму, модель и
`create_task()`. В update-режиме стадия сохраняется отдельной цепочкой
`TasksModel.set_board_column_by_row()` -> `set_task_board_column()`.

Редактирование существующей задачи проходит через
`TaskDetailsDialog._save_inline_updates()`. При наличии модели вызывается
`TasksModel.update_task_by_row()`, иначе используется прямой fallback на
`Database.update_task(task_id=...)`. Это значит, что изменение существующей
задачи является немедленной storage-операцией; отмена режима формы не является
rollback уже сохранённых inline-изменений.

В edit-режиме выбор значения и потеря фокуса запускают autosave. Перед записью
собирается единый снимок всех текущих редакторов, поэтому сохранение одного
свойства не сбрасывает ещё не сохранённый текст соседнего поля. Временная задача
с `id=0` обновляет тем же механизмом только локальный `TaskRow`.

В верхней группе параметров стадия расположена слева от проекта. Карточка
родительской задачи вынесена из верхней группы в левую колонку непосредственно
над разделом «Дополнительно» и использует уменьшенный шрифт значения.

Storage-контракт находится в
`mindnavigator/storage/database_tasks_mixin.py`:

- `create_task()` и `update_task()` валидируют проект и тип задач;
- `project_task_type_id` допускается только для того же `project_id`;
- свойства типа задач могут дать значения по умолчанию и каскадно повлиять на
  дерево задач;
- связанный concept board типа прикрепляется к задаче;
- иерархия хранится через `tasks.parent_id`;
- вложения и ссылки на сущности формы хранятся в `task_attachments` как
  `(task_id, kind, ref_id)`; внешний `ref_id` не имеет универсального SQL FK и
  проверяется прикладным кодом.

## Форма СРП проектов

### Класс и режимы

Все три режима реализует `ProjectEditDialog` из
`mindnavigator/workspaces/projects/project_edit_dialog.py`:

| Режим | Условие | Контракт |
| --- | --- | --- |
| `create` | `project is None` | Диалог сразу создаётся в edit-режиме. После `Accepted` workspace вызывает `ProjectsModel.add_project()`, затем `apply_project_properties(new_id)`. |
| `read` | передан существующий `ProjectRow` | Диалог загружает основные и дочерние свойства, затем блокирует редакторы. |
| `update` | кнопка «Редактировать» или `Ctrl+E` | После `Accepted` delegate вызывает `ProjectsModel.update_project_by_row()`, затем `apply_project_properties(project.id)`. |

`values()` возвращает только основные поля таблицы `projects`.
`apply_project_properties()` отдельно заменяет типы задач, связи, repository/wiki
links, отображаемые свойства и настройки отражения. Поэтому сохранение проекта
составное и сейчас не объединено одной внешней транзакцией между основными и
дочерними данными.

Основная запись проходит через `create_project()` и `update_project()` в
`mindnavigator/storage/database_projects_mixin.py`. Storage запрещает цикл в
`parent_project_id`, нормализует приоритеты и проверяет допустимую
периодичность.

## Форма СРП типов задач

Тип задач не имеет самостоятельного top-level класса. Его Форма СРП является
дочерней формой проекта:

- список и preview размещены в `ProjectEditDialog`;
- create/update выполняет последнее определение
  `ProjectEditDialog._task_type_dialog()`;
- read выполняют preview и строковое представление списка;
- удаление из формы запрещено, если `project_task_type_in_use(id)` возвращает
  `True`; такой тип следует деактивировать;
- изменения существуют в памяти формы проекта до вызова
  `apply_project_properties()`.

Форма редактирует `title`, `value`, цветовой и тематический маркеры, приоритет,
важность, признак плановой задачи, concept board и `active`.

Фактическая запись выполняется
`replace_project_task_types(project_id, items)` из
`mindnavigator/storage/database_project_properties_mixin.py`. Метод:

- нормализует `title` и `value`;
- обеспечивает уникальность `title`, `value` и непустого цветового маркера в
  пределах проекта;
- вызывает `add_project_task_type()` или `update_project_task_type()`;
- обновляет `sort_order`;
- физически удаляет отсутствующий тип только тогда, когда он не используется
  задачами.

В `project_edit_dialog.py` и `database_project_properties_mixin.py` есть
повторные определения методов работы с типами задач. Python использует
последнее определение в классе. При изменениях нужно либо править последнее
определение, либо сначала удалять дубликат с отдельной регрессионной проверкой.

## Связи сущностей

| Источник | Связь | Хранение и удаление |
| --- | --- | --- |
| Проект | родительский проект | `projects.parent_project_id`, `ON DELETE SET NULL` |
| Проект | карта, заметка, объект | `linked_map_id`, `linked_note_id`, `linked_object_id`, `ON DELETE SET NULL` |
| Проект | типы задач | `project_task_types.project_id`, `ON DELETE CASCADE` |
| Проект | связанные проекты | `project_related_projects`, обе стороны имеют FK; строки удаляются каскадно |
| Проект | связанные задачи | `project_related_tasks`, строки удаляются каскадно |
| Задача | проект | `tasks.project_id`; явного `ON DELETE` в актуальной схеме нет |
| Задача | родительская задача | `tasks.parent_id`; явного `ON DELETE` в актуальной схеме нет |
| Задача | тип и тип-источник откладывания | два FK на `project_task_types`, оба `ON DELETE SET NULL` |
| Задача | произвольные вложения/ссылки | `task_attachments`; FK есть только для `task_id` |

Тип задач принадлежит ровно одному проекту. Задача может выбрать тип только из
своего проекта. Проект дополнительно может ссылаться на задачи через
`project_related_tasks`; это отдельная явная связь и она не заменяет
`tasks.project_id`.

## Крупные файлы и зоны риска

Размеры на 2026-06-11:

| Файл | Строк | Риск |
| --- | ---: | --- |
| `task_details_dialog.py` | 2850 | UI, autosave, hierarchy, attachments и fallback-запись сосредоточены в одном классе. |
| `project_edit_dialog.py` | 2643 | Три режима, дочерние редакторы и повторные определения методов типов задач. |
| `database_tasks_mixin.py` | 1251 | Запись задачи связана с defaults, каскадами, планом и вложениями. |
| `database_project_properties_mixin.py` | 618 | Несколько replace-контрактов; `replace_project_task_types()` определён дважды. |
| `database_projects_mixin.py` | 411 | Иерархия проектов и защита от циклов. |

Правила изменения этих форм:

1. Сначала определить затрагиваемый режим СРП и фактический save-маршрут.
2. Для задачи отдельно проверить поведение `id=0` и существующего положительного id.
3. Для проекта проверить обе стадии записи: основные поля и `apply_project_properties()`.
4. Для типа задач проверять последнее определение метода и ограничения storage.
5. Изменение FK или каскада сопровождать migration/schema-тестом, а не только UI-тестом.
