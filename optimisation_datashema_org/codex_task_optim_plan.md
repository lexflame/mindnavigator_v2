# План оптимизации, надежности и развития связности MindNavigator

Дата первоначального анализа: 2026-06-05
Дата актуализации: 2026-06-06
Ветка актуализации: `epic/tweaks_task_mode`
Основание: статический обзор структуры приложения, storage-слоя, рабочих областей, навигации, поиска, механизмов связей и тестов; повторная сверка после вливания исходного плана и последующих изменений задач.

## 1. Краткое резюме

MindNavigator уже имеет сильную основу: локальное SQLite-хранилище с WAL для локальных БД, отдельные рабочие области, развитую модель задач, проектные свойства, связи между сущностями, контекстное связывание, drag-and-drop инфраструктуру и заметный объем тестов. На 2026-06-06 в репозитории найдено 474 тестовые функции, есть проверки миграций, CSV transfer, UI-моделей, рабочих областей и отдельных сценариев задач.

Главный риск дальнейшего развития не в отсутствии функциональности, а в концентрации сложности:

- крупные Qt/workspace файлы по 80-138 KB затрудняют изменение UI без регрессий;
- `database_schema_mixin.py` совмещает создание схемы, миграции, перестройку таблиц и индексы;
- `Database` собран из множества mixin, но нет явного доменного сервисного слоя для сценариев вроде "применить тип задачи", "связать сущности", "перенести проектный контекст";
- существуют несколько параллельных механизмов связей: `task_attachments`, `context_entity_links`, relation tables для идей, досье, коллекций, концептборда;
- поиск и часть UI-моделей перечитывают целые наборы данных и фильтруют их в памяти;
- интерфейс богатый, но местами требует слишком много ручных переходов между сущностями и режимами.

После первоначального анализа в ветку добавлены фильтр задач по верхнему проекту/области, фильтры по важности, отдельное состояние неопределенной важности, начало дня задач в 06:00 и единое оформление календарного popup. Эти изменения улучшают локальный поток работы с задачами и увеличивают покрытие тестами, но одновременно подтверждают риск дальнейшего роста `tasks_workspace.py`, `tasks_model.py` и `tasks_item_delegate.py`.

Основная рекомендация: не переписывать приложение целиком. Нужна поэтапная стабилизация вокруг трех осей:

1. Выделить доменные сервисы поверх storage для сложных сценариев.
2. Унифицировать связи сущностей в единый граф с совместимостью со старыми таблицами.
3. Разгрузить крупные UI-файлы через модели состояния, отдельные панели и переиспользуемые формы.

## 2. Карта текущей архитектуры

### 2.3. Storage и схема данных

Сильные стороны:

- SQLite включается через единый `Database`.
- Используются `foreign_keys=ON`, WAL для локальной БД, `busy_timeout`, `synchronous=NORMAL`.
- Есть адаптация journal mode для сетевых путей.
- Есть индексы по большому числу полей.
- Есть тесты миграций.

Риски:

- `get_database()` возвращает новый `Database()` при каждом вызове. Это упрощает использование, но может плодить соединения и скрывать стоимость операций.
- `check_same_thread=False` открывает путь к небезопасному доступу без явной очереди операций.
- `database_schema_mixin.py` содержит создание таблиц, ensure-методы, rebuild таблиц, foreign key repairs, user_version-логику и legacy compatibility в одном файле.
- Есть несколько мест с `PRAGMA foreign_keys=OFF`; нужны строгие проверки восстановления режима и `PRAGMA foreign_key_check` после rebuild.
- Миграции частично построены как idempotent ensure-операции, а частично как версия. Это надежно для полевых БД, но усложняет прогнозируемость.

## 3. Рекомендации по оптимизации и надежности

### 3.1. Ввести доменные сервисы поверх storage

Проблема: сложные операции сейчас часто распределены между UI-моделью и storage. Пример класса сценариев: применение типа задач проекта, каскад во вложенные задачи, возврат к обычной/плановой задаче, обновление отображаемых данных.

Рекомендация:

- создать слой `mindnavigator/domain/` или `mindnavigator/services/`;
- начать с сервисов:
  - `TaskTypeService`;
  - `TaskHierarchyService`;
  - `EntityLinkService`;
  - `ProjectContextService`;
  - `SearchService`.

Критерий готовности:

- UI вызывает один метод сценария, а не собирает SQL/каскад/refresh логику самостоятельно;
- storage остается низкоуровневым CRUD + транзакции;
- каждый сервис покрыт storage-level тестами без запуска больших Qt-диалогов.

### 3.2. Стандартизировать транзакционные сценарии

Рекомендация:

- для операций, меняющих несколько таблиц или дерево задач, ввести явные методы `run_in_transaction` или локальный helper в `DatabaseCoreMixin`;
- каскадные операции задач всегда выполнять как одну транзакцию;
- после операций с `foreign_keys=OFF` выполнять:
  - восстановление `PRAGMA foreign_keys=ON`;
  - `PRAGMA foreign_key_check`;
  - тест на rollback при ошибке.

Задачи:

- `P1-STORAGE-01`: добавить тесты rollback для сложных операций задач.
- `P1-STORAGE-02`: добавить `foreign_key_check` в migration validation tests.
- `P2-STORAGE-03`: выделить transaction helper и заменить повторяющиеся `with self._conn` в сложных сценариях.

### 3.3. Оптимизировать чтение задач и поиск

Проблема:

- `TasksModel._reload_from_db()` читает все задачи, строит дерево, пересчитывает плановые метаданные и перестраивает строки.
- `SearchNav` при каждом изменении текста синхронно проходит по нескольким fetch-методам и фильтрует в памяти.
- `ContextEntitySearchService` также перебирает сущности в памяти и использует fuzzy score на Python-уровне.

Рекомендация:

- добавить debounce 150-250 мс для глобального поиска;
- ввести limit-first SQL search по активным сущностям;
- для задач добавить специализированные fetch:
  - `fetch_tasks_for_day`;
  - `fetch_tasks_for_project`;
  - `fetch_task_tree`;
  - `fetch_tasks_search`;
  - `fetch_task_ids_with_descendants`.
- рассмотреть SQLite FTS5 для title/description/summary/preview/body_md.

Критерий готовности:

- поиск не блокирует UI при росте БД;
- модели задач не перечитывают все строки для локальных операций, кроме операций, реально меняющих дерево;
- есть performance smoke tests на условной БД 5k/20k задач.

### 3.4. Ввести измеримость производительности

Сейчас оптимизация будет субъективной без baseline.

Рекомендация:

- добавить `tests/perf/` или отдельные benchmark scripts без обязательного CI;
- измерять:
  - старт приложения до первого экрана;
  - `fetch_tasks`;
  - `TasksModel._reload_from_db`;
  - глобальный поиск;
  - открытие формы редактирования задачи;
  - открытие формы проекта;
  - миграции на копии старой схемы.

Минимальный формат:

- скрипт создает временную БД с N задач, M проектов, K связей;
- выводит p50/p95 для ключевых операций;
- результаты сохраняются в `docs/perf/`.

### 3.5. Усилить надежность БД на сетевых путях

Код уже переключает journal mode на `DELETE` для UNC/сетевых путей. Нужно закрыть риски:

- возможные долгие блокировки;
- аварийное завершение во время backup/migration;
- разное поведение WAL/DELETE.

Рекомендация:

- добавить явный health check БД в настройки:
  - journal mode;
  - foreign key check;
  - integrity check;
  - размер БД;
  - путь и признак сетевого пути.
- перед миграциями делать автоматический backup в безопасный каталог.
- добавить UX-сообщение, если БД на сетевом пути работает в более консервативном режиме.

## 4. Рекомендации по улучшению интерфейса и КПД работы с задачами

### 4.1. Сформировать "Task Command Center"

Сейчас задачи имеют несколько режимов: список, план, сегодня, выполнено, отложенные, Gantt, Board, Dash. Это мощно, но повышает стоимость навигации.

Рекомендация:

- сделать единый контекстный правый/нижний инспектор задачи;
- в нем показывать:
  - текущий проект;
  - тип задачи;
  - проектные отображаемые данные;
  - вложенные задачи;
  - связанные сущности;
  - быстрые действия: старт, завершить, отложить, применить свойства к ветке, открыть проект.

Цель: пользователь должен меньше открывать модальных форм.

### 4.2. Уменьшить зависимость от больших модальных форм

Большие формы `task_edit_dialog.py`, `task_details_dialog.py`, `project_edit_dialog.py` уже содержат много правил. Рекомендуемый путь:

- быстрые inline-редакторы для частых полей;
- отдельные малые popover-формы для редких настроек;
- единый компонент выбора сущности;
- единый компонент списка "строка + edit/delete/add icons";
- единый компонент link/display-property editor.

Критерии:

- создание/редактирование типичной задачи занимает не более 1-2 переходов;
- редактирование проекта не требует прокрутки через все секции, если меняется только один блок;
- есть consistent visual contract для малых форм.

### 4.3. Улучшить поток "проект -> задачи -> связанные материалы"

Рекомендация:

- в проекте добавить агрегированную вкладку/панель "Рабочий контекст":
  - активные задачи проекта;
  - типы задач;
  - отображаемые данные;
  - wiki/repo;
  - связанные заметки/карты/объекты;
  - последние изменения.
- в задаче показывать не только проектные ссылки, но и "почему они здесь": источник - проект, тип задачи, ручная связь.
- добавить действие "Создать задачу из проекта" с предзаполненными типами и контекстом.

### 4.4. Повысить эффективность списков

Рекомендации:

- в списке задач явно выделить наследуемые/каскадные свойства, чтобы пользователь понимал, что пришло из типа или проекта;
- добавить bulk-preview перед каскадом свойств: "будет изменено N задач";
- добавить "undo last cascade" на уровне операции, хотя бы через запись operation log;
- добавить быстрые фильтры по:
  - типу задачи проекта;
  - наличию вложенных задач;
  - наличию связей;
  - отсутствию проекта;
  - задачам с просроченным планом.

### 4.5. Сделать поиск навигационным центром

Сейчас поиск ищет по многим сущностям, но выглядит как вспомогательная панель.

Рекомендация:

- добавить keyboard-first command palette:
  - открыть сущность;
  - создать задачу;
  - связать текущую сущность с найденной;
  - перейти к проекту;
  - отфильтровать задачи;
  - выполнить команду над выбранной задачей.
- поиск должен возвращать не только entity, но и actions.

## 5. Рекомендации по связанности сущностей

### 5.1. Единый граф связей

Текущая ситуация: связи хранятся в нескольких таблицах. Это нормально исторически, но плохо для общих сценариев.

Рекомендация:

- ввести canonical таблицу `entity_links`:
  - `id`;
  - `source_kind`;
  - `source_id`;
  - `target_kind`;
  - `target_id`;
  - `link_kind`;
  - `anchor_text`;
  - `source_field`;
  - `weight`;
  - `created_at`;
  - `updated_at`;
  - `created_by_context`.
- старые tables оставить как compatibility/source-specific layer;
- сначала построить read facade, затем постепенно переводить запись.

Критерий:

- любая сущность может показать "все связанные сущности" одним API;
- связь можно создать из любой карточки;
- есть обратная навигация и удаление связи из одного места.

### 5.2. Единый Entity Identity Registry

Рекомендация:

- описать entity kind в одном месте:
  - человекочитаемое имя;
  - таблица;
  - id field;
  - title field;
  - subtitle fields;
  - icon;
  - доступные actions;
  - supported links.
- использовать registry в search, drag-drop, context linking, Entity API, UI cards.

Польза:

- меньше расхождений между `SearchNav`, `ContextEntitySearchService`, `EntityApiPool` и drag/drop;
- проще добавлять новые сущности.

### 5.3. Связи как рабочий контекст

Рекомендация:

- в каждой карточке сущности показывать блок "Контекст":
  - прямые связи;
  - входящие связи;
  - сущности того же проекта;
  - последние связанные задачи;
  - suggested links по title/tags/project.
- добавить "Link suggestions" на основе:
  - совпадения проекта;
  - совпадения слов;
  - явных ссылок в тексте;
  - общих карт/объектов.

### 5.4. Нормализовать проектный контекст

Проект сейчас выступает не только сущностью, но и контекстом для задач, wiki/repo, типов задач, отображаемых данных, связанных задач/проектов.

Рекомендация:

- явно определить `ProjectContext`:
  - inherited fields;
  - reflected fields;
  - task type rules;
  - display properties;
  - default links;
  - sync/cascade rules.
- все правила применения к задачам держать в одном сервисе.

## 8. Критерии успеха

### Надежность

- Все массовые операции задач покрыты rollback tests.
- Миграции проходят `foreign_key_check`.
- Backup перед рискованными миграциями автоматизирован.
- Сетевой путь БД явно диагностируется в настройках.

### Производительность

- Глобальный поиск не блокирует UI при 20k задач.
- Открытие списка задач остается интерактивным при 5k/20k задач.
- Открытие формы задачи не делает лишних полных перечитываний.

### UI/КПД

- Частые изменения задачи делаются inline.
- Проектный контекст виден без открытия формы проекта.
- Связанные сущности доступны из любой карточки.
- Пользователь может найти сущность и выполнить действие из одной command palette.

### Поддерживаемость

- В ключевых зонах нет файлов, которые продолжают расти без выделения компонентов.
- Storage schema и migrations разделены.
- Доменные правила задач описаны и покрыты тестами.
- Entity links имеют единый facade.

## 9. Риски и ограничения

- Нельзя резко заменить все существующие relation tables: нужна совместимость и постепенный read facade.
- Нельзя переписывать UI wholesale: слишком высокий риск регрессий в desktop behavior.
- FTS5 может потребовать отдельной migration strategy и fallback, если SQLite-сборка ограничена.
- Operation log/undo должен быть ограничен массовыми доменными операциями, а не пытаться сразу стать полной системой истории.
