# ТЗ: Реализация окна просмотра и редактирования задачи в desktop-приложении MindNavigator

## 1. Назначение задачи

Необходимо реализовать новое окно просмотра и редактирования задачи для desktop-приложения MindNavigator на Python.

Окно должно заменить или расширить текущую форму редактирования задачи и стать единой формой для двух режимов:

- просмотр задачи;
- редактирование задачи.

Интерфейс должен быть выполнен в текущем визуальном стиле MindNavigator: тёмная тема, графитовый фон, фиолетово-синие акценты, компактные карточки, мягкие границы, аккуратные поля ввода и dropdown-элементы.

В качестве визуальной логики необходимо использовать элементы, похожие на Bootstrap 4:

- `input-group`;
- `dropdown`;
- `button addons`;
- `badge`;
- `card`;
- `tabs`;
- `collapse`;
- `progress`;
- `carousel`.

Так как приложение desktop на Python, Bootstrap 4 не подключается напрямую. Его паттерны необходимо адаптировать через PySide6/QWidget/QSS.

## 2. Технологический контекст

Реализация должна быть выполнена для desktop-приложения на Python.

Основной UI-стек:

- Python;
- PySide6;
- Qt Widgets;
- QSS;
- SQLite;
- существующая архитектура MindNavigator;
- существующие модели задач, проектов, маркеров, цветов и связей.

Если в проекте уже есть собственные базовые компоненты UI, необходимо переиспользовать их.

Если подходящих компонентов нет, необходимо создать новые переиспользуемые виджеты.

## 3. Главная цель интерфейса

Окно должно ощущаться как полноценная карточка управления задачей.

Пользователь должен быстро видеть:

- название задачи;
- проект;
- срок выполнения;
- приоритет;
- важность;
- описание;
- связанные сущности;
- прикреплённые изображения;
- сферу;
- тематический маркер;
- цветовой маркер;
- повторяемость;
- планируемое и потраченное время.

Интерфейс не должен выглядеть как техническая таблица. Он должен выглядеть как удобный редактор сущности.

## 4. Общая компоновка окна

Форма состоит из трёх основных блоков:

1. Верхний блок - заголовок и ключевые свойства задачи.
2. Левая часть - описание, связи, изображения.
3. Правая часть - классификация, повторяемость, GANTT и время.

Схема компоновки:

```text
┌──────────────────────────────────────────────────────────────┐
│ Верхний блок: заголовок, проект, срок, приоритет, важность    │
├──────────────────────────────┬───────────────────────────────┤
│ Левая часть 50%              │ Правая часть 50%              │
│ Описание                     │ Сфера                         │
│ Связи                        │ Маркер тематики               │
│ Изображения                  │ Цветовой маркер               │
│                              │ Повторяемость                 │
│                              │ GANTT / время                 │
└──────────────────────────────┴───────────────────────────────┘
```

## 5. Размеры окна

Рекомендуемый размер окна:

- минимальная ширина: 1100 px;
- рекомендуемая ширина: 1200-1280 px;
- минимальная высота: 700 px;
- рекомендуемая высота: 760-820 px.

Окно должно корректно работать при изменении размера.

Минимально допустимое поведение:

- верхний блок всегда остаётся сверху;
- левая и правая части занимают по 50%;
- при малой высоте внутренние блоки должны прокручиваться;
- нижняя панель действий должна оставаться доступной.

## 6. Тип окна

Окно может быть реализовано как:

- `QDialog`;
- кастомный `QWidget` поверх основного интерфейса;
- встроенная правая/центральная панель;
- modal-like overlay.

Предпочтительный вариант: отдельное широкое окно `QDialog` или кастомная панель с затемнённым фоном.

Окно должно поддерживать:

- закрытие по кнопке;
- закрытие по `Esc`;
- сохранение по `Ctrl+Enter`;
- отмену по `Esc`, если нет несохранённых изменений;
- предупреждение при закрытии с несохранёнными изменениями.

## 7. Режимы формы

Форма должна быть единой для просмотра и редактирования.

Не должно быть двух разных окон: отдельно просмотр и отдельно редактирование.

### 7.1. Режим просмотра

В режиме просмотра:

- поля отображаются как текст, бейджи, карточки и чипы;
- элементы dropdown не должны выглядеть активными;
- описание отображается как обычный текст;
- изображения отображаются в слайдере;
- связи отображаются в виде чипов;
- справа отображаются свойства задачи;
- доступна кнопка `Редактировать`.

### 7.2. Режим редактирования

В режиме редактирования:

- название превращается в поле ввода;
- проект, срок, приоритет, важность и остальные свойства становятся изменяемыми;
- описание становится `QTextEdit` или `QPlainTextEdit`;
- связи можно добавлять и удалять;
- изображения можно добавлять, удалять и листать;
- повторяемость можно настраивать;
- GANTT-время можно редактировать;
- доступны кнопки `Сохранить` и `Отменить`.

### 7.3. Переключение режимов

При нажатии `Редактировать` форма переходит в режим редактирования.

При нажатии `Сохранить` данные валидируются, сохраняются, затем форма возвращается в режим просмотра.

При нажатии `Отменить` несохранённые изменения откатываются.


### 7.4. Частичное редактирование отдельных полей

Форма должна поддерживать не только общий режим редактирования всей задачи, но и локальное редактирование каждого отдельного поля.

Переход конкретного поля в режим редактирования осуществляется по двойному клику по соответствующему полю.

Правило поведения:

- одиночный клик по интерактивной сущности открывает связанную сущность или выполняет основное действие просмотра;
- двойной клик по редактируемому полю переводит только это поле в режим редактирования;
- остальные поля при этом остаются в режиме просмотра;
- после подтверждения значения поле возвращается в режим просмотра;
- после отмены значения поле возвращается к последнему сохранённому состоянию.

Поля, которые должны поддерживать локальное редактирование по двойному клику:

- название задачи;
- срок выполнения;
- приоритет;
- важность;
- описание;
- сфера;
- маркер тематики;
- цветовой маркер;
- повторяемость задачи;
- статус;
- плановое время;
- интервалы времени, если они отображаются внутри формы.

Для локального редактирования необходимо предусмотреть единый механизм `InlineEditableField` или аналогичный базовый компонент.

Компонент должен иметь состояния:

- `view` - отображение значения;
- `edit` - редактирование значения;
- `saving` - временное состояние сохранения;
- `error` - состояние ошибки валидации или сохранения.

Локальное редактирование не должно ломать общий режим редактирования всей формы.

### 7.5. Общий режим редактирования всей формы

Кнопка `Редактировать` переводит в режим редактирования всю форму целиком.

В этом режиме:

- все редактируемые поля становятся активными одновременно;
- dropdown-поля становятся раскрываемыми;
- описание открывается в WYSIWYG-редакторе;
- связи можно добавлять и удалять;
- изображения можно прикреплять и удалять;
- свойства задачи можно менять;
- кнопки применения свойств к вложенным элементам становятся активными;
- доступны кнопки `Сохранить` и `Отменить`.

Кнопка `Сохранить` сохраняет все изменённые поля одной транзакцией или единым вызовом сервисного слоя.

Кнопка `Отменить` откатывает все несохранённые изменения формы.

### 7.6. Навигация по сущностям одиночным кликом

Одиночный клик по полям, которые представляют связанные сущности, должен выполнять переход к этой сущности.

Переход по одиночному клику должен быть реализован для:

- поля `Проект`;
- чипов в блоке `Связи`;
- элементов навигатора концептборда, если они являются ссылками на сущности;
- связанных задач;
- связанных идей;
- связанных заметок;
- связанных файлов;
- связанных объектов или карт, если они поддерживаются текущей архитектурой.

Если форма находится в режиме просмотра, одиночный клик открывает сущность.

Если форма находится в режиме редактирования, одиночный клик по значению не должен случайно менять поле. Для открытия сущности в режиме редактирования можно использовать отдельную иконку перехода или контекстное меню.

### 7.7. Разрешение конфликта одиночного и двойного клика

Необходимо явно обработать различие между одиночным и двойным кликом.

Правило:

- одиночный клик по сущности запускает переход после небольшой задержки, достаточной для определения двойного клика;
- двойной клик отменяет действие одиночного клика и переводит поле в режим редактирования, если поле редактируемое;
- для нерекомендуемых к редактированию ссылок двойной клик может повторять открытие сущности.

Рекомендуется реализовать это через общий обработчик кликов или базовый компонент поля, чтобы поведение было одинаковым во всей форме.

## 8. Верхний блок

Верхний блок занимает 100% ширины окна.

### 8.1. Содержимое верхнего блока

Верхний блок содержит:

- название задачи;
- проект;
- срок выполнения;
- приоритет;
- важность задачи;
- кнопку закрытия;
- индикатор режима просмотра/редактирования.

### 8.2. Название задачи

Название задачи должно быть главным визуальным элементом окна.

В режиме просмотра:

- отображается крупным текстом;
- рядом может быть цветовая точка задачи;
- рядом может быть статус задачи.

В режиме редактирования:

- используется поле ввода;
- высота поля увеличенная;
- стиль похож на `form-control-lg` из Bootstrap 4.

Требования:

- пустое название запрещено;
- максимальная длина должна соответствовать текущей модели данных;
- при пустом названии показывать ошибку валидации.

### 8.3. Проект

Проект отображается как dropdown/input-group.

Паттерн:

```text
[ Проект ][ MindCore ▼ ]
```

В PySide6 реализовать через один из вариантов:

- `QComboBox`;
- `QToolButton + QMenu`;
- кастомный `InputGroupDropdown`.

Требования:

- список проектов загружается из текущего источника данных;
- выбранный проект сохраняется в задаче;
- должен быть вариант `Без проекта`, если он допустим в модели;
- проект должен иметь визуальный бейдж.

### 8.4. Срок выполнения

Срок выполнения отображается как input-group.

Паттерн:

```text
[ Срок ][ Сегодня 23:59 ▼ ]
```

Состав:

- дата;
- время;
- быстрые действия.

Dropdown быстрых действий:

- Сегодня;
- Завтра;
- На этой неделе;
- Без срока;
- Выбрать дату;
- Выбрать дату и время.

Требования:

- дата и время должны сохраняться отдельно, если так устроена текущая модель;
- если время не задано, показывать только дату;
- если срок просрочен, отображать состояние `Просрочено`.

### 8.5. Приоритет

Приоритет отображается как dropdown с цветом и иконкой.

Значения:

- Высокий;
- Средний;
- Низкий;
- Без приоритета, если поддерживается.

Визуальная логика:

- высокий: красно-розовый акцент;
- средний: оранжево-жёлтый акцент;
- низкий: зелёный акцент.

Паттерн:

```text
[ Приоритет ][ ↑ Высокий ▼ ]
```

### 8.6. Важность задачи

Добавить отдельное свойство `Важность задачи`, если оно уже есть в модели. Если свойства нет, необходимо подготовить реализацию с безопасной интеграцией.

Варианты представления:

- шкала от 1 до 5;
- текстовые уровни;
- звёзды;
- числовой рейтинг.

Предпочтительный вариант:

```text
[ Важность ][ ★★★★☆ ▼ ]
```

Значения:

- 1 - низкая;
- 2 - умеренная;
- 3 - обычная;
- 4 - важная;
- 5 - критичная.

Если в базе данных нет поля важности, необходимо добавить миграцию или расширить модель безопасным способом.

## 9. Левая часть окна

Левая часть занимает 50% ширины окна.

Левая часть содержит:

- описание;
- связи;
- слайдер изображений.

Каждый блок должен быть оформлен как карточка.

## 10. Блок `Описание`

### 10.1. Назначение

Блок содержит основное текстовое описание задачи.

### 10.2. Режим просмотра

В режиме просмотра описание отображается как текст внутри карточки.

Если описание пустое, показывать muted-placeholder:

```text
Описание пока не добавлено
```

### 10.3. Режим редактирования

В режиме редактирования поле `Описание` должно использовать WYSIWYG-редактор на базе `QTextEdit` или собственного редактора поверх `QTextEdit`.

Простой `QPlainTextEdit` для основного режима описания не использовать, если требуется форматирование текста.

WYSIWYG-редактор должен открываться:

- при переходе всей формы в режим редактирования по кнопке `Редактировать`;
- при двойном клике по блоку `Описание` в режиме просмотра;
- при выборе действия `Редактировать описание` из контекстного меню блока.

### 10.3.1. WYSIWYG-редактор описания

Редактор должен быть встроен прямо в блок `Описание`, без открытия отдельного окна.

Верхняя часть блока `Описание` должна содержать компактную панель инструментов.

Минимальный набор инструментов:

- жирный текст;
- курсив;
- подчёркивание;
- зачёркивание;
- выбор типа заголовка: обычный текст, H2, H3;
- маркированный список;
- нумерованный список;
- цитата;
- inline-code;
- вставка ссылки;
- вставка изображения или ссылки на изображение, если это поддерживается текущей моделью;
- выравнивание: слева, по центру, справа;
- отмена действия;
- повтор действия.

Дополнительные инструменты, если их можно реализовать без усложнения:

- цвет текста;
- выделение маркером;
- чеклист;
- горизонтальная линия;
- очистить форматирование;
- переключение `WYSIWYG / Markdown / HTML preview`.

Визуальный пример панели:

```text
[ B ][ I ][ U ][ S ] [ H2 ▼ ] [ • list ][ 1. list ][ ❞ ][ code ]
[ link ][ image ][ align-left ][ align-center ][ align-right ][ undo ][ redo ]
```

Требования к поведению:

- панель инструментов должна быть компактной и не занимать больше одной строки при обычной ширине окна;
- если места недостаточно, часть инструментов уходит в кнопку `Ещё`;
- активные форматирования должны подсвечиваться;
- редактор должен сохранять форматирование в формате, совместимом с текущей моделью данных;
- если в проекте уже используется Markdown, хранить Markdown и отображать preview;
- если используется HTML, хранить ограниченный безопасный HTML;
- запрещены небезопасные HTML-теги и inline-скрипты;
- при вставке текста из буфера необходимо очищать лишние стили;
- счётчик символов должен отображаться в правом нижнем углу блока;
- при пустом описании показывать placeholder `Описание пока не добавлено`.

### 10.3.2. Режим просмотра WYSIWYG-описания

В режиме просмотра описание отображается как отформатированный текст.

В режиме просмотра не показывать панель инструментов.

Ссылки внутри описания открываются по одиночному клику.

Двойной клик по текстовой области описания переводит блок `Описание` в режим редактирования.

### 10.3.3. Сохранение описания

При локальном редактировании только блока `Описание` должны быть доступны малые действия внутри блока:

- `Сохранить описание`;
- `Отменить`.

При общем редактировании всей формы описание сохраняется вместе со всеми остальными полями по кнопке `Сохранить`.


### 10.4. Требования

- поле должно поддерживать многострочный текст;
- высота блока должна быть удобной;
- описание не должно съедать всю форму;
- при большом описании должна появляться внутренняя прокрутка.

## 11. Блок `Связи`

### 11.1. Назначение

Блок отображает сущности, связанные с задачей.

Поддерживаемые типы связей:

- задачи;
- идеи;
- заметки;
- проекты;
- файлы;
- изображения;
- объекты;
- карты, если поддерживаются текущей архитектурой.

### 11.2. Визуальное представление

Связи должны отображаться в виде компактных чипов.

Пример:

```text
[ Задача #124: Базовые компоненты × ]
[ Идея: Наследование свойств × ]
[ Заметка: Архитектура компонентов × ]
[ + Добавить связь ]
```

### 11.3. Поведение

В режиме просмотра:

- одиночный клик по чипу открывает связанную сущность;
- кнопка удаления скрыта;
- двойной клик по блоку `Связи` переводит блок в локальный режим редактирования связей.

В режиме редактирования:

- можно добавить связь;
- можно удалить связь;
- можно открыть связанную сущность через отдельную кнопку перехода или контекстное меню;
- можно выбрать тип связи через dropdown.

Переход к связанной сущности должен быть явным и быстрым, но не должен конфликтовать с редактированием самой связи.

### 11.4. Добавление связи

Кнопка:

```text
+ Добавить связь
```

При нажатии открывается dropdown или popup:

- выбрать тип сущности;
- найти сущность через поиск;
- выбрать из списка;
- подтвердить привязку.

### 11.5. Требования

- не допускать дублирующиеся связи;
- не допускать битые связи;
- при удалении связи не удалять саму связанную сущность;
- хранить связь в текущей таблице связей, если она уже существует;
- если таблицы связей нет, подготовить отдельный слой хранения.

## 12. Блок `Изображения`

### 12.1. Назначение

Блок отображает изображения, привязанные к задаче.

### 12.2. Визуальное представление

Использовать desktop-аналог Bootstrap carousel.

В PySide6 можно реализовать через:

- `QStackedWidget`;
- кнопки `Назад` и `Вперёд`;
- индикатор `1 / N`;
- область предпросмотра;
- миниатюры, если есть место.

### 12.3. Состояние без изображений

Если изображений нет, показывать:

```text
Изображения не прикреплены
[ + Прикрепить изображение ]
```

### 12.4. Режим просмотра

В режиме просмотра:

- изображения можно листать;
- одиночный клик выбирает изображение или показывает быстрый preview;
- двойной клик по изображению открывает отдельный слайдер просмотра всех изображений задачи;
- удаление недоступно.

### 12.4.1. Слайдер просмотра изображений по двойному клику

Двойной клик по любому изображению открывает отдельное окно или overlay-слайдер.

Назначение слайдера:

- просмотр всех изображений, привязанных к задаче;
- переход назад и вперёд между изображениями;
- просмотр изображения в увеличенном размере;
- добавление комментария к текущему изображению;
- просмотр уже добавленных комментариев к текущему изображению.

Слайдер должен содержать:

- крупную область изображения;
- кнопку `Назад`;
- кнопку `Вперёд`;
- индикатор `N / Всего`;
- список комментариев к изображению;
- поле добавления комментария;
- кнопку `Добавить комментарий`;
- кнопку закрытия.

Комментарии к изображению должны привязываться не к файлу глобально, а к изображению только в рамках конкретной задачи.

Это означает:

- один и тот же файл изображения может использоваться в разных задачах;
- комментарии в одной задаче не должны отображаться в другой задаче;
- комментарии должны хранить связь `task_id + image_id`;
- при удалении связи изображения с задачей комментарии к этой связке должны быть скрыты или удалены согласно принятой политике хранения.

Рекомендуемая структура хранения комментариев:

```text
task_image_comments
  id INTEGER PRIMARY KEY
  task_id INTEGER NOT NULL
  image_id INTEGER NOT NULL
  comment_text TEXT NOT NULL
  created_at TEXT
  updated_at TEXT
```

Если в проекте уже есть универсальная таблица комментариев, использовать её, но обязательно сохранить привязку комментария к паре `задача + изображение`.

### 12.5. Режим редактирования

В режиме редактирования:

- можно добавить изображение;
- можно удалить изображение;
- можно открыть изображение;
- можно листать изображения.

### 12.6. Требования

- изображения должны подгружаться безопасно;
- большие изображения должны масштабироваться;
- интерфейс не должен зависать при открытии формы;
- если изображение отсутствует на диске, показывать заглушку;
- путь к изображению не должен ломать открытие задачи.

## 13. Правая часть окна

Правая часть занимает 50% ширины окна.

Правая часть содержит:

- сферу;
- маркер тематики;
- цветовой маркер;
- повторяемость задачи;
- GANTT / время.

Блоки должны быть оформлены карточками.

## 14. Блок `Свойства`

### 14.1. Назначение

Блок содержит классификационные свойства задачи.

Состав:

- сфера;
- тематический маркер;
- цветовой маркер;
- повторяемость задачи.

Каждое свойство должно использовать паттерн Bootstrap 4 input-group.

Общий вид:

```text
[ Сфера             ][ Архитектура компонентов ▼ ]
[ Маркер тематики   ][ Analysis ▼                 ]
[ Цветовой маркер   ][ Синий ▼                    ]
[ Повторяемость     ][ Без повтора ▼              ]
```


### 14.2. Кнопки применения свойств к вложенным элементам

Для свойств `Проект`, `Приоритет`, `Важность`, `Сфера`, `Маркер тематики`, `Цветовой маркер` необходимо добавить кнопку справа от поля для применения выбранного свойства к вложенным элементам задачи.

Кнопка должна быть частью input-group и располагаться справа от значения поля.

Визуальный паттерн:

```text
[ MindCore ▼ ][ применить к вложенным ]
[ Высокий ▼ ][ применить к вложенным ]
```

Иконка кнопки: `fa6.square-caret-down`, `fa6.share-nodes`, `fa6.sitemap` или существующая иконка проекта для наследования.

При нажатии кнопки открывается меню применения:

- применить только к прямым подзадачам;
- применить ко всем вложенным подзадачам;
- применить только к выбранным вложенным элементам;
- применить к подзадачам без собственного значения;
- отмена.

Действие должно требовать подтверждения, если затрагивается больше одного вложенного элемента.

Пример подтверждения:

```text
Применить свойство «Проект: MindCore» ко всем вложенным задачам?
Будет изменено: 7 элементов.
[ Отмена ][ Применить ]
```

Требования:

- кнопка применения свойства активна только в режиме редактирования всей формы или при локальном редактировании соответствующего поля;
- в режиме просмотра кнопка может быть скрыта или отображаться как disabled;
- после применения свойства необходимо обновить вложенные элементы и визуальное состояние формы;
- операция должна быть атомарной, насколько это возможно в текущем слое данных;
- при ошибке применения показать сообщение и не скрывать форму.

## 15. Сфера

## 18. Повторяемость задачи

### 18.1. Назначение

- Каждый день;
- Каждую неделю;

### 18.4. Расширенный режим

- изменение повторяемости не должно ломать обычные задачи;
- поля расширенного режима должны быть скрыты, если повтор не используется.

## 19. Блок `GANTT / Время`

### 19.1. Назначение

Блок отображает время, связанное с задачей:

- планируемое время;
- потраченное время;
- оставшееся время;
- временные интервалы работы.

Это не должен быть полноценный сложный GANTT-модуль. Нужен компактный task-level GANTT.

### 19.2. Визуальное представление

Пример:

```text
GANTT / Время задачи

План:       4 ч
Потрачено: 1 ч 30 мин
Осталось:  2 ч 30 мин

[████████░░░░░░░░░░] 37%

Сегодня
09:00 - 10:30  Анализ
14:00 - 15:00  Исправление логики
```

### 19.3. Компоненты

Использовать desktop-аналоги:

- `QProgressBar`;
- `QListWidget` или кастомный список интервалов;
- `QSpinBox` для часов;
- `QSpinBox` для минут;
- `QTimeEdit`;
- `QDateEdit`;
- dropdown для типа активности.

### 19.4. Поля

Минимальный набор:

- planned_minutes;
- spent_minutes;
- remaining_minutes, вычисляемое поле;
- progress_percent, вычисляемое поле.

Если в базе нет таких полей, подготовить миграцию или отдельную таблицу учёта времени.

### 19.5. Интервалы работы

Если реализуется хранение интервалов, использовать структуру:

- task_id;
- start_datetime;
- end_datetime;
- duration_minutes;
- comment;
- activity_type.

### 19.6. Требования

- прогресс рассчитывается автоматически;
- остаток рассчитывается автоматически;
- если плановое время равно 0, прогресс не должен ломаться;
- потраченное время не должно быть отрицательным;
- интервалы можно добавлять и удалять в режиме редактирования;
- в режиме просмотра интервалы только отображаются.


## 19.7. Навигатор концептборда вместо блока учёта времени

В правой нижней части формы вместо отдельного блока `Учёт времени` должен отображаться блок `Навигатор концептборда`.

Блок `GANTT / Время` остаётся компактным индикатором планового и потраченного времени, но не должен превращаться в расширенный журнал учёта времени внутри основного окна задачи.

`Навигатор концептборда` должен показывать связанные концептуальные элементы задачи в виде цепочки или мини-графа:

```text
Идея → Заметка → Концепт → Узел
```

Назначение блока:

- быстро показать, из какой идеи или заметки выросла задача;
- показать связь задачи с концептбордом;
- дать быстрый переход к связанному концепту;
- дать возможность добавить или открыть концепт.

Одиночный клик по элементу навигатора открывает соответствующую сущность.

Двойной клик по редактируемому элементу навигатора переводит его в локальный режим редактирования, если такое редактирование поддерживается.

## 19.8. Сворачиваемые блоки `Связи` и `Изображения`

Блоки `Связи` и `Изображения` должны поддерживать сворачивание и разворачивание через стрелку в заголовке блока.

По умолчанию в режиме просмотра блоки `Связи` и `Изображения` должны быть свёрнуты.

При сворачивании блоков:

- содержимое блока скрывается;
- заголовок остаётся видимым;
- стрелка меняет направление;
- блоки визуально смещаются вниз;
- блок `Описание` автоматически увеличивается по высоте и занимает освободившееся место.

В режиме редактирования допустимо автоматически раскрывать блоки, если пользователь добавляет связь или изображение.

Состояние свёрнутости можно сохранять в пользовательских настройках окна.

## 23. Данные задачи

5. Переключение в режим просмотра.
6. При редактировании создание временной копии данных.
7. При сохранении валидация.
8. Сохранение через существующий слой данных.
9. Обновление списка задач после сохранения.

## 24. Модель данных

entity_links

## 26. Стилизация QSS

Окно должно соответствовать текущей тёмной теме MindNavigator.

Основные визуальные требования:

- фон окна: тёмный с сине-графитовым оттенком;
- карточки: чуть светлее основного фона;
- поля: тёмные, с мягкой границей;
- активные элементы: фиолетово-синий акцент;
- hover: лёгкое осветление;
- focus: акцентная рамка;
- disabled: muted-состояние;
- dropdown: тёмный фон, читаемые пункты;
- badge: компактный, скруглённый;
- progress: в текущей акцентной палитре.

Не менять общую цветовую схему приложения.

## 27. Иконки

Использовать существующий механизм иконок проекта.

Если используется QtAwesome, применить иконки:

- закрыть: `fa6.xmark`;
- редактировать: `fa6.pen`;
- сохранить: `fa6.check`;
- отменить: `fa6.ban`;
- раскрыть dropdown: `fa6.square-caret-down`;
- дата: `fa6.calendar-days`;
- время: `fa6.clock`;
- связь: `fa6.link`;
- изображение: `fa6.image`;
- добавить: `fa6.plus`;
- удалить: `fa6.trash`;
- назад: `fa6.chevron-left`;
- вперёд: `fa6.chevron-right`.

## 28. Валидация

При сохранении проверить:

- название задачи не пустое;
- дата корректна;
- время корректно;
- приоритет входит в допустимый список;
- важность находится в диапазоне 1-5;
- planned_minutes не меньше 0;
- spent_minutes не меньше 0;
- связи не дублируются;
- выбранные справочники существуют.

Ошибки показывать рядом с полем или в верхней части окна.

Форма не должна закрываться при ошибке сохранения.

## 29. События и обновление интерфейса

После успешного сохранения необходимо:

- обновить список задач;
- обновить карточку задачи, если она открыта в другой части интерфейса;
- обновить фильтры, если изменился проект, срок, статус или маркеры;
- обновить план, если изменились дата или время;
- сохранить состояние выбранной задачи.

## 30. Горячие клавиши

Добавить поддержку:

- `Ctrl+Enter` - сохранить;
- `Esc` - закрыть или отменить;
- `Ctrl+E` - перейти в режим редактирования;
- `Ctrl+S` - сохранить без закрытия;
- `Delete` - удалить выбранную связь или интервал, если фокус внутри соответствующего блока.

## 31. UX-детали

Требования:

- форма не должна выглядеть перегруженной;
- вторичные настройки прятать в collapse/dropdown;
- все ключевые поля должны быть видны без прокрутки;
- визуальная иерархия должна быть понятной;
- название задачи всегда должно быть главным элементом;
- свойства должны быть сгруппированы;
- опасные действия не должны находиться рядом с основной кнопкой сохранения;
- в режиме просмотра форма должна быть спокойной;
- в режиме редактирования интерактивные элементы должны быть явно видны.

## 32. Обработка пустых состояний

Для пустых данных показывать понятные placeholder-состояния.

Примеры:

```text
Описание пока не добавлено
Связи отсутствуют
Изображения не прикреплены
Повторяемость не настроена
Плановое время не задано
```

## 33. Производительность

Окно должно открываться быстро.

Требования:

- не загружать тяжёлые изображения синхронно в основном потоке;
- масштабировать изображения до предпросмотра;
- не выполнять лишние запросы к базе;
- справочники можно кэшировать;
- связанные сущности подгружать ограниченно;
- большие списки в dropdown должны поддерживать поиск или фильтрацию.

## 34. Совместимость

Необходимо сохранить совместимость с текущим функционалом:

- список задач;
- фильтры;
- план задач;
- проекты;
- статусы;
- маркеры;
- подзадачи;
- текущая логика сохранения задач.

Новая форма не должна ломать старые сценарии создания и редактирования задачи.

## 35. Интеграция с созданием задачи

Если задача создаётся с нуля, использовать эту же форму.

Для новой задачи:

- открывать форму в режиме редактирования;
- название пустое;
- проект можно подставлять из текущего контекста;
- дата может подставляться из текущего режима планирования;
- приоритет по умолчанию: Средний или текущий дефолт проекта;
- важность по умолчанию: 3;
- повторяемость: Без повтора;
- planned_minutes: 0;
- spent_minutes: 0.

## 36. Интеграция с подзадачами

Если задача имеет подзадачи, необходимо предусмотреть место для будущего расширения.

На первом этапе подзадачи можно не включать в основную компоновку, если они уже есть в отдельной вкладке.

Допустимый вариант:

- добавить вкладку `Подзадачи`;
- либо добавить compact-блок в правой части ниже GANTT;
- либо оставить ссылку `Открыть подзадачи`.

Необходимо не конфликтовать с существующей логикой наследования свойств подзадач.

## 37. Результат реализации

После выполнения задачи должно быть реализовано:

- новое окно просмотра/редактирования задачи;
- единый режим view/edit;
- верхний блок с основными свойствами;
- левая колонка с описанием, связями и изображениями;
- правая колонка со сферой, маркерами, повторяемостью и GANTT-временем;
- адаптированные Bootstrap 4-паттерны через PySide6;
- QSS-стилизация в текущей цветовой схеме;
- сохранение изменений в модель задачи;
- валидация;
- обработка пустых состояний;
- обновление списка задач после сохранения;
- локальное редактирование каждого поля по двойному клику;
- переход к проекту и связям по одиночному клику;
- WYSIWYG-редактор для описания;
- отдельный слайдер изображений с комментариями в рамках задачи;

## 38. Критерии приёмки

Задача считается выполненной, если:

- окно открывается из списка задач;
- окно корректно отображает существующую задачу;
- форма имеет верхний блок на 100% ширины;
- форма имеет левую и правую части по 50%;
- название задачи редактируется;
- проект выбирается через dropdown;
- срок выполнения редактируется;
- приоритет выбирается через dropdown;
- важность задачи отображается и редактируется;
- описание отображается и редактируется;
- связи отображаются в виде чипов;
- связи можно добавлять и удалять в режиме редактирования;
- изображения отображаются в слайдере;
- изображения можно добавлять и удалять в режиме редактирования;
- сфера выбирается через dropdown;
- тематический маркер выбирается через dropdown;
- цветовой маркер выбирается через dropdown;
- повторяемость выбирается через dropdown;
- расширенные настройки повторяемости скрываются и раскрываются корректно;
- GANTT-блок отображает план, потраченное время, остаток и прогресс;
- данные сохраняются;
- список задач обновляется после сохранения;
- при ошибках сохранения форма не закрывается;
- двойной клик по отдельному полю переводит только это поле в режим редактирования;
- одиночный клик по проекту открывает проект;
- одиночный клик по связи открывает связанную сущность;
- кнопка `Редактировать` переводит всю форму в режим редактирования;
- описание редактируется через WYSIWYG-редактор;
- двойной клик по изображению открывает слайдер всех изображений задачи;
- в слайдере изображений можно добавлять комментарии к изображению в рамках текущей задачи;
- кнопки применения свойств к вложенным элементам есть у проекта, приоритета, важности, сферы, тематического маркера и цветового маркера;
- блоки `Связи` и `Изображения` могут быть свёрнуты и по умолчанию свёрнуты в режиме просмотра;
- при сворачивании блоков `Связи` и `Изображения` блок `Описание` автоматически увеличивается;
- вместо отдельного блока `Учёт времени` используется блок `Навигатор концептборда`;
- горячие клавиши работают;
- цветовая схема соответствует текущему интерфейсу MindNavigator;
- старый функционал задач не сломан.
